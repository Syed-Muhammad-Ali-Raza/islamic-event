- [x] Phase 49: Actionable rate-limit feedback — a throttled request used to render the same generic banner as a wrong password, so a user hitting 12 sign-ups or 10 failed logins per 15 minutes had no idea when to retry (and React Query happily retried a 429 once, burning more of the budget). - [x] Phase 50: Edge caching for public reads — production measurements showed every public page answering `Cache-Control: private, no-store` (they read `searchParams`, so Next.js renders them dynamically) with `/dastarkhwan` at 1.4-1.8 s TTFB and totals up to 10 s after an idle API/Neon, and `next.config.js` cache rules cannot override that: they now do apply to the prerendered routes (`/`, `/privacy`, `/terms`, `/organizers` answer `public, s-maxage=60, stale-while-revalidate=300`, verified live) but Next still forces `no-store` on the dynamic ones, so the fix moved to the data layer. New `apps/api/src/middleware/cache.middleware.ts` marks the 14 non-personalised GET prefixes (categories, cities, organizers, people, dastarkhwans, imambargahs, places, darbars, urs-dates, processions, charities, melas, auqaf-urs-dates, scholars) `public, s-maxage=60, stale-while-revalidate=300`, and deliberately skips any request carrying an `Authorization` header plus all non-GET/HEAD methods, applying the header only when a 2xx response head is written so a 404 (unknown `sourceId`), 429 or 5xx is never pinned at the edge — `/events*` stays uncached because its list and detail payloads embed `isSaved`/`myRsvp` for the caller, and `/auth*`, `/admin`, `/approvals`, `/notifications`, `/users`, `/internal` and `/upload` are excluded by the allow-list. Live proof: `GET /api/v1/dastarkhwans` answers `X-Vercel-Cache: MISS` then `HIT` with `Age: 1`, the same URL with a bearer token answers `X-Vercel-Cache: BYPASS`, and the same URL twice over 10 trials gave a median TTFB of 0.94 s (miss/function) vs 0.51 s (edge hit) — a 46% cut on the read path that the web app's SSR fetches now hit.
